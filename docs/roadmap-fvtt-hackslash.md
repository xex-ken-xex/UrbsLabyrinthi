# 展開メモ（FVTT の半自動TRPG と、ハックアンドスラッシュ）

## 0. この資料について

Urbs Labyrinthi を土台にして、次の二つへ進むための下調べと、段取りの案。

1. FVTT に組み込み、NPC とダンジョンを自動で動かす、GM なしの半自動TRPG
2. Unity か Godot で作る、ハックアンドスラッシュのアクションゲーム

| タグ | 意味 |
|---|---|
| 【確認済】 | 2026-10-08 に、公式の資料で確かめた |
| 【要確認】 | 記憶や推測で書いた。実機か公式資料で確かめてから使う |
| 【案】 | 進め方の提案。決定ではない |
| 【未確定】 | 決めること |

コードは一行も試していない。API の名前や定数は、【確認済】と書いたもの以外、動かす前に確かめること。

---

## 1. 二つの企画で共有するもの

| 共有するもの | いまある場所 | FVTT での使い方 | ハクスラでの使い方 |
|---|---|---|---|
| 地図の生成（種と夜） | Urbs Labyrinthi の `Core.generate` | そのまま JavaScript で動く | 移植するか、JSON を読む |
| 書き出し JSON（urbs-labyrinthi/0.1） | `Core.exportJSON` | シーン、壁、扉、駒、領域に変換する | タイルマップ、敵の配置、罠に変換する |
| 魔物データ（SRD、CC-BY-4.0） | 軽量 JSON 2版 | dnd5e システムの収録データを名前で引く | 数値を換算して使う |
| 層の定義（部屋名、描写、罠、対応表） | `Core.THEMES` | 語りと罠の文言 | ステージの見た目と敵の出現表 |
| 夜ごとの組み替え、吐く夜 | `nightInfo`、種の二本立て | 夜が替わるたびに、壁と駒を張り替える | 潜るたびに通路が変わる。吐く夜は高難度の日 |
| 自動GMの応答の形 | 仕様 §6.3 | LLM と自動進行のあいだの約束 | 使わない（会話や依頼文の生成に流用できる） |

先に JSON を固めておくと、二つの企画が同じ迷宮を別の形で遊べる。【案】JSON の版を上げるときは、`schema` の番号を変える。

## 2. FVTT の半自動TRPG

### 2.1 いまの FVTT（2026年10月）

| 項目 | 内容 |
|---|---|
| 最新の安定版 | **14.368**（2026-09-16）【確認済】 |
| バージョン14 の最初の安定版 | 14.359（2026-04-01）【確認済】 |
| バージョン13 の最後の安定版 | 13.351（2025-11-12）【確認済】 |
| 13 から 14 への更新 | 上書き更新はできない。入れ直しになる。先にユーザーデータを控える【確認済】 |
| dnd5e システム | **5.3.3**。最低 13.347、検証ずみ 14。コードは MIT、収録データは SRD 5.1 と 5.2（CC-BY-4.0）【確認済】 |
| dnd5e の収録パック | 2014年版: `monsters`（Monsters (SRD)）、`spells`、`items` など。2024年版: `actors24`、`spells24`、`equipment24` など【確認済】 |

**バージョン14 で変わった点のうち、この企画に関わるもの**【確認済】

- **シーン・レベル**: 一つのシーンに、高さの違う画像を重ねられる。視界、移動、戦闘が階をまたぐ。壁や灯りを階ごとに割り当てられる → 迷宮の「層」を、一つのシーンにまとめる道がある【案】
- **霧の共有**: 誰かが見た範囲を、全員に開く探索モードが入った → Urbs Labyrinthi の霧と同じ遊び方になる
- **計測テンプレートの廃止**: 領域（Region）に置き換わった。範囲攻撃を扱うモジュールは、14 対応かどうかを確かめる
- **アクティブ・エフェクト V2**: 効果の期限と、期限切れの出来事を細かく扱える。駒の見た目も変えられる

### 2.3 罠と出来事は、領域（Region）で起こす

FVTT の領域には、あらかじめ次の振る舞いと出来事がある【確認済】。

| 振る舞い | 使いみち |
|---|---|
| スクリプトの実行（Execute Script） | 罠の発動、部屋の読み上げ、遭遇の開始 |
| マクロの実行（Execute Macro） | 同上。マクロにまとめておく場合 |
| 駒の転送（Teleport Token） | 階段、落とし穴 |
| ゲームの一時停止（Pause Game） | 山場の前で止める |
| 流れる文字の表示（Display Scrolling Text） | 短い描写 |
| 移動コストの変更（Modify Movement Cost） | 瓦礫、水 |
| 暗さの調整、天候の抑制、振る舞いの切り替え | 灯りのある部屋、一度きりの罠 |

出来事は、駒が入る、出る、中で動く、ターンを始める、ターンを終える、ラウンドを始める、ラウンドを終える、など。

【案】罠の流れ

1. 駒が罠の領域に入る → スクリプトが、駒の受動〈知覚〉と `detect_dc` を比べる
2. 気づいたら、チャットに手がかりを出して止める。気づかなければ、発動
3. 発動したら、`save` の能力と難易度でセーヴを求める（dnd5e の判定を呼ぶ）。`damage` を振り、`half_on_success` を見て適用する
4. 「振る舞いの切り替え」で、罠を使用ずみにする

### 2.4 自動進行の組み立て【案】

**前提（大事）**: FVTT では、ワールドを書き換える処理は、GM の権限でつながっているクライアントが実行する。サーバーだけでは動かない。GM なしで遊ぶには、**GM 役のブラウザを一つ、無人で開いておく**必要がある【要確認】。既存のモジュール Familiar も「ワールドへの変更は、すべて GM のクライアントを通す」と説明している【確認済】。

| 層 | 役目 | 作り方 |
|---|---|---|
| ① 盤面の管理 | 夜の切り替え、シーンの張り替え、霧のリセット | 自作モジュール。`Core.generate` をそのまま載せ、§2.2 の変換をかける |
| ② 規則の実行 | 命中、ダメージ、セーヴ、状態、イニシアチブ | dnd5e システムに任せる。自動適用は、既存の自動化モジュールを使うか、最小限を自作する【未確定】 |
| ③ 魔物の頭（規則） | 誰を狙うか、どこへ動くか、いつ逃げるか | まず**決め打ちの規則**で作る。LLM は使わない（§2.5） |
| ④ 語りと裁定（LLM） | 部屋の描写、探索の判定の提案、交渉、魔物の意図の言葉づけ | 自動GMの応答の形（仕様 §6.3）で受け取り、①〜③が実行する |
| ⑤ 進行役の代わり | 「次に何が起きるか」を決める輪 | 出来事（領域、戦闘のターン、チャットの発言）を拾って、③か④へ回す |

- **LLM に数値を決めさせない**。命中やダメージは②が振り、LLM は `intent` と語りだけを返す。Urbs Labyrinthi のプロンプトの「数値はデータのまま使い、変えない」と同じ考え方
- **伏せ札を混ぜない**。応答の `hidden` は GM 役のクライアントだけが持ち、プレイヤーへは `narration` と `choices` だけを送る
- LLM の呼び出しは、GM 役のクライアントから外部の API へ出す形になる。鍵の置き場所と料金は別途決める【未確定】

### 2.5 魔物の頭（規則）の最初の版【案】

Urbs Labyrinthi が遭遇ごとに付けている `attitude`（敵対、警戒、交渉の余地あり）と `kind`（mindless / beast / smart）を、そのまま入力に使う。

| 種類 | 狙う相手 | 動き | 引き際 |
|---|---|---|---|
| mindless（不死、粘体、人造、植物） | いちばん近い相手 | まっすぐ近づく。機会攻撃を気にしない | 逃げない |
| beast（野獣、群れ） | いちばん近い相手。次に、HP の少ない相手 | 囲む。群れは同じ相手に集まる | HP が半分を切り、仲間が半分倒れたら逃げる |
| smart（それ以外） | 後衛、回復役、集中を保っている相手 | 遠隔攻撃があれば距離を取る。扉や通路の狭さを使う | HP が1/4 を切ったら逃げるか、降参する。`attitude` が「交渉の余地あり」なら、最初に声をかける |

行動の選び方は、「いま使える攻撃のうち、期待ダメージ（命中率 × 平均ダメージ）が最大のもの」。命中率は (21 ＋ 攻撃ボーナス − 相手の AC) ÷ 20 を、0.05〜0.95 に収める。

## 3. ハックアンドスラッシュ

### 3.1 何を持ち越し、何を変えるか

| 項目 | TRPG 版 | ハクスラ版【案】 |
|---|---|---|
| 地図 | 5フィートのマス、幅1マスの通路 | 同じ生成器。1マス＝1.5m として、通路は2〜3マス幅に広げる |
| 時間 | ラウンド（6秒）とターン | リアルタイム。ラウンド単位の数値を、秒あたりに直す |
| 霧 | 見た範囲が残る | 同じ。視界は、光源と遮蔽で毎フレーム計算する |
| 夜と種 | 夜の番号で通路が変わる | 「今日の迷宮」。同じ日は全員が同じ地図になる。吐く夜は高難度の日 |
| 魔物 | SRD の能力値 | 換算して使う（§3.2） |
| 罠 | セーヴと難易度 | 予兆を見て避ける。難易度は、予兆の長さと範囲に置き換える |
| 稼ぎ | XP と燐晶 | 燐晶が通貨。持ち帰った分の3割が税。深いほど純度が高い |
| 物語 | 物語の種、帳面 | 拾える遺留品、断片の文章 |
| 引き返す判断 | 封鎖令、帰還 | 「潜るほど稼げるが、戻れなければ全部失う」。封鎖令は時間切れの仕組みに使える |

### 3.2 SRD の数値の換算【案】

| SRD | 意味 | アクションでの置き換え |
|---|---|---|
| HP、ヒット・ダイス | 耐久力 | そのまま。難度ごとに倍率をかける |
| AC | 当たりにくさ | **案1**: 被ダメージの軽減率 ＝ (AC − 10) × 3%。**案2**: 正面からの攻撃を弾く確率。アクションでは、外れより軽減のほうが手触りがよい |
| 攻撃ボーナス | 当てやすさ | 使わない（当たり判定は見た目で決まる）。または、攻撃の速さや追尾の強さに回す |
| ダメージ・ダイス | 一撃の重さ | 平均値を使う（1d6＋2 → 5.5）。ばらつきは ±15% ほどに抑える |
| 複数回攻撃 | 手数 | 連続技の段数 |
| 移動速度 | 30フィート／ラウンド | 30フィート ＝ 9m を6秒で ＝ 秒速1.5m。これは歩きの速さなので、戦闘中は2〜3倍する |
| 能力値 | 筋敏耐知判魅 | 敏捷 → 回避の間隔、判断・知力 → 行動パターンの賢さ（§2.5 の三種）に使う |
| 抵抗、完全耐性、脆弱 | 属性 | そのまま、0.5倍、0倍、2倍 |
| 状態への完全耐性 | 効かない状態 | そのまま |
| 脅威度、XP | 強さの目安 | 出現表の予算（仕様 §3.2）にそのまま使える。倒したときの経験値と、落とす燐晶の量 |
| 特徴（Pack Tactics など） | 固有の能力 | 名前しか持っていない。**一つずつ、動きとして作り直す**。ここがいちばん手間 |

- 行動の賢さは、FVTT 用の「魔物の頭」（§2.5）と同じ三種で作れば、二つの企画で考え方を共有できる
- 層の魔物（洞窟鼠、粘泥など）は固有名なので、名前と見た目は自由。数値の出どころが SRD なら、帰属表示は要る（データ資料 §3）

### 3.3 生成器の持ち込み方

| 方法 | 手間 | 向き |
|---|---|---|
| **JSON を読む** | 小 | 最初はこれ。ツールで作った地図を、そのままステージにする。生成器を直しても、ゲーム側は変えなくてよい |
| 生成器を移植する | 中 | ゲームの中で無限に作りたくなったら。`Core.generate` は約270行 |
| JavaScript のまま動かす | 中 | Web に出す場合や、エンジンに JavaScript を載せる場合 |

**移植するときの注意**

- **乱数をそのまま移す**。ツールは xmur3 と mulberry32（32ビットの整数演算）を使っている。エンジン付属の乱数に替えると、同じ種でも別の地図になる。ツールと同じ地図を出したいなら、この二つを同じ式で書く。GDScript の整数は64ビットなので、掛け算のたびに下位32ビットへ切り詰める【要確認】
- **乱数を引く順番を変えない**。途中に一回足すだけで、以降がすべて変わる
- 移植したら、同じ種でツールの JSON と一致するかを、自動で比べる。ツールの側では、900通りで再現性を確かめてある

### 3.4 エンジンごとの当てはめ

**どちらを選ぶかの観点**【未確定】（費用や出力先の事情は変わりやすい。決める前に、公式ページで確かめる【要確認】）

| 観点 | Godot | Unity |
|---|---|---|
| 費用とライセンス | MIT。無料 | 料金体系がある。規模で変わる |
| 2D の作りやすさ | 2D 専用の仕組みが軽い | 2D も 3D も同じ土台 |
| 言語 | GDScript（C# も使える） | C# |
| 素材と情報 | 増えているが、Unity より少ない | アセットストアと日本語の情報が多い |
| 出力先 | PC、Web、モバイル。家庭用ゲーム機は外部の業者経由 | 幅広い |
| この企画との相性 | 生成器の移植と 2D の霧は、どちらでも同じ手間 | 同左 |

一人で 2D を作り、費用をかけず、まず動くものを見たいなら Godot。3D にしたい、アセットを買って早く形にしたい、家庭用ゲーム機まで見ているなら Unity。**どちらにするかは、3D にするかどうかで、ほぼ決まる**。
